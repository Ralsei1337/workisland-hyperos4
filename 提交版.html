一、方案与设计

工作岛 · 方案与设计

版本 1.4 · 2026-10-26 设备：OnePlus PJA110 · ColorOS 16.0.3（Android 16 / SDK 36） 宿主：cccodroid 0.4.2（包名 cc.codroid）

摘要

「工作岛」把 cccodroid 里 Claude 的实时运行状态，显示在 ColorOS 16 的流体云（灵动岛）上：

  • 进行中：正在干活 + 当前动作（用执行命令 / 正在想 / 等你确认…）
  • 完成：任务完成 + 用时
  • 8 秒后：岛上收起，通知栏保留一条安静的「在后台等下一轮」

数据不是模拟的，来自 cccodroid 网关的真实事件流（/api/events、/api/state）。整个方案不修改 cccodroid 的 Java 代码，只做两处可回退的网关接入。

1. 背景与问题

cccodroid 是运行在 Android 上的 Claude Code 宿主：它有一个 Node 网关（server.mjs，监听 127.0.0.1:8791），负责会话、运行队列、事件流和通知。

原生通知是普通通知，不会自动变成 ColorOS 的流体云胶囊。要上岛，需要 Android 16 的 Live Updates（实时更新）资格：

  • 通知使用 Notification.ProgressStyle 等标准样式；
  • 声明 POST_PROMOTED_NOTIFICATIONS 权限；
  • 通知为 ongoing，带标题，不使用自定义视图；
  • 通过 android.requestPromotedOngoing 请求推广（promoted）。

在实现过程中遇到并解决了四个真问题：

问题 现象 根因
普通通知不上岛 只有通知栏，没有胶囊 没有 promoted / ProgressStyle
完成后不收起 岛上一直挂着「正在干活」 监听器跟着单轮 Claude 进程被收走
定时器不生效 「任务完成」永不收起 ColorOS 把应用冻住（do_freezer_trap），进程内定时器不走
提前报完成 还在干活就显示「任务完成」 把「最近一轮」当成「所有轮次」，换轮空隙 run 短暂为空

2. 目标与非目标

目标

  1. 岛上显示 真实 的 Claude 工作状态（阶段 / 工具 / 完成），不是写死动画。
  2. 视觉与 cccodroid 统一：深色 #1F1E1D、陶土色 #D97757、鱼形图标。
  3. 后台可用：cccodroid 切后台、工作岛切后台、屏幕关闭时仍能更新。
  4. 收工准确：只有所有运行轮次都结束才报完成；连续两轮之间不闪「完成」。
  5. 可回退：对 cccodroid 的改动只有两个文件，原文件有备份。

非目标

  • 不接管 cccodroid 的聊天 UI、不修改它的 Java/ dex。
  • 不做到「ccc odroid 被强行停止后仍然工作」——没有宿主就没有任务可显示。
  • 不自定义胶囊的像素级外观（胶囊由系统绘制，第三方只能控制图标、标题、文本、进度）。
  • 不承诺跨设备通用：当前实现针对 Android 16 / ColorOS 16。

4. 运行流程

4.1 首次接入

  1. 安装 WorkIsland.apk，授予通知权限。
  2. 系统设置里开启「允许实时更新」（canPostPromotedNotifications() 为 true）。
  3. 网关启动时执行 server.mjs 里的 startWorkIsland()： - 读取 ~/.work-island.pid，若对应进程仍活着就复用； - 否则 spawn(process.execPath, [driver.mjs])，detached + unref，并删除环境里的 CCAPP_RUN（避免被网关的孤儿清理误杀）。
  4. driver 读取 ~/.gateway-token（0600，仅 cccodroid uid 可读），订阅 http://127.0.0.1:8791/api/events。
  5. driver 通过 am start-foreground-service --user 0 驱动工作岛；工作岛拉起前台服务并画通知。

4.2 一轮任务

用户发消息
  → 网关 run_start
  → driver 置 working，发 UPDATE「正在干活 / 正在处理…」
  → 模型思考 / 调工具：phase=think / tool / tool_use
  → 岛上实时更新「正在想…」「用 执行命令…」
  → 权限确认：perm_request → 「等你确认」
  → 回答后：perm_resolved → 「继续…」
  → run_end
  → driver 不立刻报完成，先等 2.5s 回 /api/state 复查
       ├─ runs 还有 → 说明是别的轮次结束，忽略
       └─ runs 为空 → 进入 3s 宽限
              ├─ 3s 内来了新 run_start → 取消完成，接着干
              └─ 没有新 run → 发 DONE「任务完成 / 用时 X」
                     └─ 8s 后发 IDLE → 换成 ID 1002 安静通知，岛上收起

5. 事件到文案

driver 把网关事件翻译成岛上的短句（尽量 6 个字以内，避免胶囊截断）：

事件 岛上文本
run_start 正在处理…
phase=wait 等模型回复…
phase=think 正在想…
phase=text 正在写回复…
phase=tool / tool_use 用 执行命令… / 读文件… / 改文件… / 搜代码… / 查资料…

工具名映射：Bash→执行命令、Read→读文件、Write/Edit→写/改文件、Grep→搜代码、WebSearch→查资料、Task/Agent→子任务、TodoWrite→整理清单 等。

标题会跟着动作走：读文件 / 执行命令 / 思考中 / 等模型 / 写回复 / 等你确认 / 整理清单 / 后台任务 / 出错了。文本保留更长的描述；TodoWrite 显示「清单 x/y」。完成时标题用「任务完成」。

6. 收工判定：四道关

这是整个项目踩坑最多的地方，单独说明。

  1. 看 runs，不看 run /api/state 里 run 是“最近开始的一轮”，换轮的空隙可能短暂为空；runs 才是“所有正在跑的轮次”。只要 runs 非空，就不算完。
  2. run_end 后 2.5 秒复查 收到 run_end 不直接发完成，先 setTimeout 2500ms，再 GET /api/state；runs 为空才继续。
  3. 不按 runId 直接排除 换轮时 active.id 可能还是上一轮的，按 id 排除会漏掉真正的结束；统一用第 2 步的状态复查。
  4. 完成前 3 秒宽限 复查通过后再等 3 秒；期间来了新 run_start 就取消完成，继续「正在干活」。这避免了连续两轮之间闪一下「任务完成」。

完成之后还有 8 秒的展示期，然后 IDLE 收起；新的一轮开始会取消 IDLE 定时器。

7. 关键技术

7.1 Android 16 Live Updates 与 ColorOS 16

ColorOS 16 的流体云已经接入 Google 的 Android 16 Live Updates 规范。满足资格的通知会被系统提升为胶囊，无需 OPPO 的私有白名单；OPPO 自家的 UPK 卡片是另一条路，需要业务资格。

资格要求（实测）：

  • 使用标准样式（本项目用 Notification.ProgressStyle）；
  • 声明 android.permission.POST_PROMOTED_NOTIFICATIONS；
  • setOngoing(true)，有 contentTitle；
  • 不使用 customContentView，不是 group summary，未 colorized；
  • 通知渠道重要性不是 IMPORTANCE_MIN（本项目用 IMPORTANCE_LOW）；
  • 请求 promoted（见 7.2）。

7.2 推广（promoted）的开启方式

平台公开的 Notification.Builder 没有 setRequestPromotedOngoing 方法，但系统里有：

  • 额外字段键：android.requestPromotedOngoing（布尔）；
  • 隐藏方法：Notification.Builder#setRequestPromotedOngoing(boolean)。

实现同时做两件事：

Bundle extras = new Bundle();
extras.putBoolean("android.requestPromotedOngoing", true);
builder.addExtras(extras);
try {
    Notification.Builder.class
        .getMethod("setRequestPromotedOngoing", boolean.class)
        .invoke(builder, true);
} catch (Throwable ignored) { /* 失败也不影响普通通知 */ }

# flags=ONGOING_EVENT|ONLY_ALERT_ONCE|NO_CLEAR|FOREGROUND_SERVICE|PROMOTED_ONGOING

项 进行中 / 完成 待机
通知 ID 1001 1002
样式 ProgressStyle（indeterminate / 100%） 普通通知
promoted 是 否

为什么待机要换 ID： 同一个 ID 的 FGS 通知在更新时可能保留 PROMOTED_ONGOING 标志，导致岛上不收起；换到 1002、取消 1001，胶囊就干净地消失。

为什么用 ProgressStyle 而不是普通进度条： 普通 setProgress 不满足 Live Update 的样式资格；ProgressStyle 才能进入流体云。

7.4 ColorOS 的后台冻结

实测发现：即使应用有前台服务、通知是 promoted，ColorOS 仍会在后台把进程冻住：

/proc/<pid>/task/<tid>/wchan = do_freezer_trap

后果：应用里的 Handler.postDelayed、Thread.sleep、SSE 读取都停住，8 秒收起永远不会发生。

结论：定时器和事件流不能放在工作岛应用里。 它们被搬到 driver，driver 跑在 cccodroid 网关的进程树里；网关是用户正在使用的宿主，不会被冻。工作岛退化成一个“只负责画”的渲染器，每次 am intent 把它短暂唤醒，画完继续冻着也没关系。

7.5 进程树与生命周期

driver 的两种部署方式：

  1. 网关模块 spawn（生产）：gw/work-island.mjs 在网关启动时 spawn，detached + unref，父进程是网关；网关每 30 秒检查一次 PID 文件，挂了就重启。
  2. 网关终端里跑（调试/兜底）：POST /api/term/new 建终端，输入 while true; do node driver.mjs; sleep 2; done； 进程链是 node server.mjs → ptyhost → bash → node driver.mjs，同样不属于单轮 Claude。

两种方式通过 ~/.work-island.pid 去重：PID 对应进程的 cmdline 含 driver.mjs 就复用。

7.6 am 的限制

从应用 uid 直接 am broadcast 会失败：

SecurityException: broadcast asks to run as user -2 but is calling from uid u0aXXXX;
requires android.permission.INTERACT_ACROSS_USERS_FULL

解决：

  • 显式加 --user 0；
  • 改用 am start-foreground-service --user 0 -n ...，既绕开跨用户限制，又能把被冻结的工作岛唤醒；
  • 失败重试两次（间隔 0.8 秒），覆盖“刚装完 APK、服务还没起来”的瞬时错误。

7.7 构建链（设备上无 Android SDK）

设备上只有 aapt2 / d8 / apksigner / javac，没有 Android SDK、没有 Gradle、没有 zipalign。构建步骤：

  1. 下载 platform-36_r02.zip，取出 android-36/android.jar（编译用，27 MB）。
  2. aapt2 compile --dir res -o res.zip
  3. aapt2 link -I android.jar --manifest AndroidManifest.xml --java gen -o base.apk res.zip
  4. javac -source 11 -target 11 -classpath android.jar -d classes ...
  5. d8 --lib android.jar --min-api 36 --output dex classes.jar
  6. zip -j base.apk dex/classes.dex
  7. apksigner sign --ks island.keystore ...

resources.arsc 由 aapt2 产出时已经是未压缩且 4 字节对齐（实测 data offset % 4 == 0），因此没有 zipalign 也能安装。签名用自签名证书；重新签名会让已安装应用需要卸载重装。

7.8 保活

工作岛侧：

  • 前台服务（specialUse）+ android:stopWithTask="false"：从最近任务划掉不停止服务；
  • BOOT_COMPLETED 接收器：开机后恢复待机通知；
  • REQUEST_IGNORE_BATTERY_OPTIMIZATIONS：界面上的「后台保活设置」按钮；
  • 已加入 deviceidle 白名单，standby bucket 设为 active。

cccodroid 侧：

  • 网关本身是前台服务；
  • 已加入 deviceidle 白名单；
  • ColorOS 自己的「自启动」「最近任务锁定」需要用户手动开启（adb 管不到）。

边界： 强行停止（force-stop）会杀掉一切，任何应用都无法自救；重新打开 cccodroid 后网关模块会重新拉起 driver。这是 Android 的规则，不是缺陷。

7.9 程序化 bot：四态、标识与体征

1.3 之前，岛上图标是「模型形状 + 两只眼睛」的简笔版。1.4 按 jazzenchen/agent-hud-open （Apache-2.0）的 BotState / BotSigns / BotSpec / BotRenderer 逐项移植成 Java，形成一套完整的 「灵魂」：

四种阶段（Wakes / Works / Asks / Done）

阶段 look 岛上表现
Wakes idle 只显示该 agent 的 logo（鲸鱼、星芒、立方体……）
Works plain / 思考 / 压缩 / 四种 tool logo 0.5 秒变成 bot；呼吸、眨眼、干活时鳍扑腾
Asks permission / question / plan bot 蹦一下、睁大眼睛；头顶 ! / ? / ≡
Done done 弹一下、笑眼（^^），2.4 秒后安静

14 种 look 与 7 个标识

LOOKS  permission question plan compacting thinking
       tool-edit tool-command tool-read tool-long-command
       plain no-news idle asleep done
SIGNS  !  ?  ≡  ×  ⧗  …  z

标识按优先级取第一个：permission ! > question ? > plan ≡ > failed × > badge ⧗ > thinking … > asleep z。字形是 5×7 点阵，绘制时带一圈 1 px 的暗色描边和 35% 的 淡格，… 的亮点会随节拍在三个格子里跳。

BotSpec：每个 agent 的体征

20 个内置 mark + Agent HUD + 小鱼，各自的字段：

  • 轮廓：圆 / 圆角矩形 / 多边形 / 猫耳 / bob / outline（从素材 alpha 径向采 360 点、 两次滑窗平滑）。所以形状跟着素材走，不是手画的近似。
  • 配色：纯色、线性渐变，或从素材采样出的 60×60 配色场（3 次盒式模糊）。
  • 眼睛：高度、宽度、圆角、间距、是否平排（across），可单独指定 eyeColor； Copilot 保留素材本身的眼窝，用 ownEyes 在上面画会动的眼睛。
  • 装饰：Claude 的手脚（像素块四肢）、DeepSeek 的浅色肚子、Grok 的土星环、 Cursor 的缺口、OpenCode 的像素块、Pi 的腿、Hermes 的云、OpenClaw 的触须、Qoder 的绿光。
  • 状态表情：睁眼 / 眨眼 / 眯眼 / 睁大 / 笑眼 / 叉眼；crossesEyes 的 mark 在出错时叉眼。

渲染与动效

  • 归一化坐标：一个 mark 占 1×1，四周留 0.3；通知小图标 160 px，大图标 256 px。
  • 应用内 BotView 逐帧跑完整动效：0.5 s logo→bot 变形、3 s 呼吸、2.2–4.5 s 随机眨眼、 请求时 0.45 s 起跳、完成时 0.6 s 弹一下、思考时眼睛向上瞟并转动。
  • 通知图标是静态帧，不能逐帧动；但每次状态更新都会重画，四态和标识是准的。

开关与回退

Prefs.soul 默认开。设置页的「程序化 bot（四态 + 标识 + 体征）」关掉后，通知图标退回 1.2 的简笔画法；应用内仍可预览。

岛上信息：别让胶囊空着

  • 折叠胶囊用 Notification.Builder.setShortCriticalText()：显示「工作状态 + 清单进度」， 例如 思考中 1/4、等你确认、整理清单 2/4。ColorOS 的流体云优先显示这段文字， 比只放一个短标题更满。
  • 展开通知：
  • 标题 整理清单 · 1/4；
  • 副标题（setSubText）正在改 BotPainter · 清单 1/4，原来的 cccodroid 换掉；
  • setUsesChronometer(true) 提供实时计时；
  • ProgressStyle.setProgressSegments()：清单有几条就分几段，已完成的段用状态色， 没完成的段用 20% 白；进度条上的 tracker 还是那只 bot。
  • 没有清单时退回原来的状态名，进度条保持 indeterminate，不硬凑步骤。

动效：通知图标也会动

通知的小图标本来是静态位图，ColorOS 又会在后台冻结应用，应用内定时器不可靠。 所以动画帧由 driver（跑在网关进程里）推：

  • 思考时每 800 ms 发一帧 --ei anim 0/1/2：省略号的亮点从左跳到右，眼睛左右瞟， 身体上下浮 1.8%；应用只负责按帧重画。上一帧的 am 返回后才发下一帧，避免排队。
  • 通知 ID 始终是 1001：同一个 ID 的更新也会刷新前导图标（thinking / error 两态实测像素不同）； 不换 ID，胶囊就不会收回再弹出（主人叫它「抽搐」）。
  • 第一帧直接是最终 bot，不再发 morph 0/45/80 唤醒帧：第一帧是 logo 时会被系统缓存一整轮， 看起来像「模型被切掉」。
  • 图标按 (模型, look, 失败, 尺寸, morph, anim) 做 24 张 LRU 缓存，同一 ID 更新时不再每帧重新渲染， 减少闪白。
  • 身体比例恒定：图标永远给头顶标识预留位置（即使当前没有 !/?/≡）， 所以标识出现/消失时 bot 不会忽大忽小，也不会贴边被圆形槽裁掉。

9. 安全与隐私

  • 网关只监听 127.0.0.1，并且所有 /api/* 需要令牌；令牌文件 0600，只有 cccodroid uid 能读。
  • driver 以 cccodroid uid 运行，读取令牌，但 不把令牌写进命令行、日志或工作岛；工作岛只接收 intent。
  • 工作岛的 IslandService 是 exported 的，同机其他应用可以伪造 START/DONE（只影响显示，不影响数据）。生产化时应加 signature 级自定义权限，或改为只允许同 uid/同签名调用。
  • 不采集、不上传任何屏幕、位置、剪贴板或会话内容；岛上只显示当前动作的短句。
  • 对 cccodroid 的改动可回退：server.mjs.original 是原文件，server.mjs 只多了一行 import 和一行启动调用。

10. 已知限制

  1. 强行停止：ccc odroid 被 force-stop 后，网关和 driver 都没了，岛上会停在最后一个状态；重开 cccodroid 恢复。
  2. ColorOS 冻结：工作岛在后台会被冻，不能自己计时；本方案把计时放在 driver，但如果 driver 也被硬杀，收起可能延迟。
  3. 应用更新：ccc odroid 更新可能覆盖 files/app/gw/work-island.mjs 与 server.mjs，需要重新接入（原文件有备份）。
  4. 胶囊外观：由系统绘制，只能控制图标、标题、文本、进度；不能自定义成 OPPO UPK 那种完全自定义卡片。
  5. exported 服务：见第 9 节，属于演示级安全。
  6. 单实例：driver 只跟踪一个“当前状态”；并行多轮时，文案可能跟随最后触发的事件，但收工判定仍以 runs 为准。

11. 后续演进

  • 给工作岛 service 加签名级权限，杜绝伪造 intent。
  • 在 driver 里加心跳（每 15–30 秒），配合 AlarmManager 看门狗，缩短硬杀后的残留时间。
  • 把 driver 的路径/端口做成配置，支持开发端 8790 与 cccodroid 8791。
  • 增加可选的胶囊文案模板（例如显示会话标题、token 用量）。
  • 如果 OPPO 开放 UPK 资格，可做完全自定义的胶囊卡片。
  • 把网关模块做成可安装组件（跟随 cccodroid 更新自动重放），减少手工接入。

终端进程链是 node server.mjs → ptyhost → bash → node driver.mjs，不属于单轮 Claude，因此不会被单轮收尾带走。

4.5 去重

  • driver 启动时把 PID 写进 ~/.work-island.pid。
  • 网关模块启动时读这个文件，检查对应进程的 cmdline 是否包含 driver.mjs；是就复用，不重复拉起。
  • 模块每 30 秒检查一次，driver 挂了会自动重启。

5. driver 行为说明

driver.mjs 的关键逻辑：

读 ~/.gateway-token
  → SSE 订阅 /api/events
  → run_start / hello.run / state.run → 开始
  → phase / tool_use / perm_request → 更新文案
  → run_end → 等 2.5s → GET /api/state → runs 为空？
       否 → 忽略（别的轮次）
       是 → 等 3s → 有新 run_start？
              是 → 取消完成
              否 → 发 DONE → 8s → 发 IDLE
  → 每 5s 轮询 /api/state 兜底
  → SIGTERM / SIGINT / SIGHUP → 发 IDLE 再退出

发送方式：

am start-foreground-service --user 0 \
  -n com.dafeiyu.workisland/.IslandService \
  -a com.dafeiyu.workisland.UPDATE \
  --es title "正在干活" --es text "用 执行命令…" \
  --el since <startedAt>

失败会自动重试两次（间隔 0.8 秒）。

6. 未覆盖 / 限制

  • force-stop 后恢复：无法在不结束当前会话的情况下测试；设计上依赖重开 cccodroid 后网关模块拉起 driver。
  • 重启开机自启：BOOT_COMPLETED 接收器已声明，但未实际重启验证；ColorOS 的自启动开关需要用户手动打开。
  • 长时间 Doze：只测了屏幕打开、后台 8 秒；未做 30 分钟以上的 Doze 测试。
  • 并行多轮文案：岛上的短句可能跟随最后触发的事件；收工判定仍以 runs 为准。
  • exported 服务伪造：同机应用可以发 START/DONE，属于演示级安全，生产化需加签名权限。
  • 自定义胶囊外观：未做 OPPO UPK 卡片，胶囊由系统绘制。

2. 遇到的坑与修法

2.1 普通通知不上岛

  • 现象：通知只在通知栏，没有胶囊。
  • 原因：没有 ProgressStyle，也没有请求 promoted。
  • 修法：Notification.ProgressStyle + POST_PROMOTED_NOTIFICATIONS + android.requestPromotedOngoing（额外字段 + 隐藏方法反射）。
  • 验证：flags=…|FOREGROUND_SERVICE|PROMOTED_ONGOING。

2.2 完成后不收起

  • 现象：任务结束，岛上还挂着「正在干活」。
  • 原因：监听器挂在单轮 Claude 的进程树里，轮次结束被一起收走，没来得及发「完成」。
  • 修法：监听移到网关进程树；后来按上游 review 进一步改成网关进程内订阅。

2.3 定时器不生效

  • 现象：应用内的 8 秒收起定时器不走。
  • 原因：ColorOS 在后台冻结应用，连前台服务也冻： /proc/<pid>/task/<tid>/wchan = do_freezer_trap。
  • 修法：定时器与事件流放到网关里的 driver/模块；工作岛只负责画。

2.4 提前报完成

  • 现象：还在干活，岛上显示「任务完成」。
  • 原因：把「最近一轮」run 当成「所有轮次」；换轮空隙 run 短暂为空。
  • 修法： 1. 看 runs，不只看 run； 2. run_end 后 2.5 秒回 /api/state 复查； 3. 只认自己的 runId（后来改为统一用 runs 复查）； 4. 完成前再等 3 秒宽限，期间来了新的一轮就取消完成。

2.5 am 的跨用户限制

  • 报错：broadcast asks to run as user -2 … requires INTERACT_ACROSS_USERS_FULL。
  • 修法：显式 --user 0；改用 am start-foreground-service，既绕开限制又能唤醒被冻结的应用；失败重试两次。

2.6 pm 的跨用户限制

  • 报错：runListPackages … asks to run as user 10 … INTERACT_ACROSS_USERS_FULL。
  • 修法：pm list packages --user 0；包可见性由清单 <queries> 解决。

二、后台保活与自动恢复

2.1 发生了什么

2026-10-25 夜里到 10-26 早上，工作岛应用被系统杀掉了：

  • 应用进程、前台服务、通知全部消失；
  • cccodroid 的网关和 driver 还活着；
  • 早上岛上没有任何状态，直到手动打开一次「工作岛」才恢复。

这不是驱动的问题，是 Android / ColorOS 把应用停掉了。

2.2 为什么会这样

  1. ColorOS 的电池管理会杀后台。前台服务（FGS）不是免死金牌；深度睡眠/应用速冻/省电策略都可能把进程停掉。
  2. Android 10+ 禁止后台启动 Activity。ccc odroid 的 driver 用 am start 起不来一个被系统停掉的应用；设备工具同样被挡。
  3. Shizuku 当时没在跑，所以 priv（shell 身份）也帮不上忙。
  4. 强行停止（force-stop）是设计上不可自救的：应用被标记为 stopped 后，广播、闹钟、JobScheduler 都不会再唤起它，直到用户手动打开。

2.3 恢复能力矩阵

场景 能否自动恢复 说明
划掉最近任务 能 stopWithTask=false，服务继续跑
系统内存回收（普通 kill） 通常能 START_STICKY + 闹钟看门狗
ColorOS 深度睡眠/速冻 看情况 进程被杀后，闹钟/看门狗可尝试拉起；被 force-stop 则不行
强行停止（force-stop） 不能 必须手动打开应用，或重启手机（BOOT_COMPLETED）
重启手机 能 BOOT_COMPLETED 接收器会拉起服务
Shizuku 在跑 能补一刀 shell 身份可以 am start-foreground-service 拉起被停的应用

2.4 ColorOS 推荐设置（手动）

这几步 adb 管不到，需要在系统设置里点：

  1. 设置 → 应用 → 应用管理 → 工作岛 → 耗电管理 - 选「允许后台活动」/「不优化」。
  2. 设置 → 应用 → 自启动 - 把「工作岛」打开。
  3. 最近任务 → 长按工作岛卡片 → 锁定 - 防止划掉/清理时被带走。
  4. 设置 → 电池 → 更多 → 睡眠待机优化 - 把「工作岛」设为「不优化」。
  5. 如果开了「应用速冻」/「深度睡眠」，把工作岛加入白名单。

工作岛应用内已经有「后台保活设置」按钮，会跳到电池优化页；状态行显示「电池：不优化」才算生效。

2.5 App 侧看门狗（待实现）

计划在应用里加一个 AlarmManager 定时器：

  • 每 15 分钟发一次 PendingIntent 给 WatchdogReceiver；
  • 接收器检查服务是否在跑，不在就 startForegroundService；
  • 如果通知已经过期/丢失，重新发一条待机通知。

限制：force-stop 后闹钟会被取消，仍然需要手动打开；Doze 下闹钟可能被延后，不能保证分钟级准时。

2.6 Driver 侧兜底（可选）

driver 的 am start-foreground-service 失败时，可以再试一次 priv -- am start-foreground-service ...：

  • 前提：Shizuku 在运行；
  • 优点：shell 身份可以拉起被系统停掉的应用；
  • 缺点：多一个 Shizuku 依赖；priv 命令会进审计日志。

当前只在个人部署里考虑，没有加进上游 PR 的默认路径。

2.7 验证方法

  1. 打开「工作岛」，确认状态行：通知开 / 实时更新允许 / 电池不优化。
  2. 正常划掉最近任务，等 8 秒：服务应还在（岛还挂着或待机通知还在）。
  3. 用 Shizuku 执行 am force-stop com.dafeiyu.workisland： - 预期：应用停掉，岛消失；am start/设备工具都起不来； - 手动打开应用后恢复。
  4. 用 am kill com.dafeiyu.workisland（普通 kill）： - 预期：START_STICKY 或闹钟看门狗把它拉回来。
  5. 重启手机：开机后应自动出现待机通知。

2.8 限制

  • force-stop 不可自救，这是 Android 的设计，不是应用 bug。
  • 不同 ColorOS 版本的设置项名称略有差异；找不到时按「电池 / 自启动 / 后台活动」三个关键词找。
  • 闹钟看门狗在 Doze 下可能延迟；不能替代 ColorOS 白名单。
  • 不建议为了保活去要 root；风险大于收益。

三、建议

  1. 先把 2.4 的五个开关都打开——这是最有效的一步。
  2. 加上 2.5 的闹钟看门狗，覆盖普通 kill / 系统回收。
  3. Shizuku 如果常开，可以在 driver 里加 priv 兜底；不常开就不加。
  4. 接受 force-stop 需要手动打开这一条，不要为它引入 root。
